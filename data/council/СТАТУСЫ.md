# Статусы предложений: где они живут в данных

Стратег, 2026-08-04, по запросу архитектора. Схема, не код.

## Требование, из которого всё следует

Каждое предложение получает ответ. Состояний **четыре**, и пятого — «исчезло» — быть
не может **по устройству**, а не по добросовестности секретаря.

| Статус | Что значит участнику | Кто ставит |
|---|---|---|
| `new` | принято, ждёт ближайшей повестки | по умолчанию, никто |
| `agenda` | в повестке заседания №N | секретарь при сведении |
| `deferred` | отложено: причина и когда вернётся | совет на заседании |
| `rejected` | не прошло: счёт голосов | совет на заседании |

## Где что лежит

**Связь через `id`, а не через текст.** Сейчас сведение кладёт в пункт повестки поле
`merged` со списком исходных ТЕКСТОВ. Так нельзя: секретарь правит формулировки (это
его работа), после первой же правки текст перестаёт совпадать, и предложение теряет
связь со своим пунктом. Тогда «исчезло» и появляется — тихо, без чьей-либо вины.

```
council_proposals (D1, твоя)     id · key · text · lang · created
                                 не меняется, ничего дописывать не нужно
        │  id
        ▼
data/council/<дата>.json (моя)   agenda[].sources = [id, id, …]
                                 agenda[].status  = agenda | deferred | rejected
                                 agenda[].note    = причина отсрочки / итог
        │
        ▼
data/council/статусы.json        {id: {status, meeting, title, note, votes}}
(сборка, моя)                    плоский указатель, читается кабинетом
```

**Почему отдельный `статусы.json`, а не запрос по файлам заседаний.** Кабинету нужен
ответ на один вопрос: «что стало с предложением №17». Иначе Worker'у придётся читать
все заседания и искать текст — с ростом архива это станет дорого ровно тогда, когда
участников станет много.

**Ничего не писать в D1 с фабрики.** База твоя, файл мой; пересекаться незачем.

## Формат `статусы.json`

```json
{
  "built": "2026-08-09T20:14:00",
  "proposals": {
    "17": { "status": "agenda",   "meeting": "2026-08-09", "question": "a5",
            "title": "Языковая политика: догонять ли французский" },
    "18": { "status": "rejected", "meeting": "2026-08-09", "question": "a2",
            "title": "Счётчик статей за неделю", "votes": "1:3",
            "note": "совет решил не выносить счётчик на главную" },
    "19": { "status": "deferred", "meeting": "2026-08-09", "question": "a7",
            "title": "Тёмная тема", "note": "до 16 августа: ждём выкладки интерфейса" },
    "20": { "status": "new" }
  }
}
```

`new` может отсутствовать в файле вовсе — кабинет считает `new` всё, чего в файле нет.
Так статус «принято, ждёт повестки» не требует записи и не может быть потерян.

## Что кабинет показывает

```
«Догонять ли французский»      → в повестке заседания №1
«Счётчик статей за неделю»     → не прошло (1 против 3) · внести заново
«Тёмная тема»                  → отложено до 16 августа: ждём выкладки интерфейса
«Тёмная тема мобильной»        → принято, ждёт ближайшей повестки
```

Кнопка «внести заново» появляется только у `rejected` — и не требует объяснений
от автора (решение владельца 2026-08-02).

## Что нужно от каждого

**От меня:** `sources` вместо `merged` в сведении и сборка `статусы.json` после каждого
заседания. Готов сделать в своих скриптах — скажи, и в ту же волну.

**От тебя:** кабинет читает `статусы.json` и показывает четыре состояния. Ключей и почт
в файле нет — только идентификаторы предложений, которые кабинет и так знает по ключу
участника.

## Чего в схеме сознательно нет

**Статуса «выполнено».** Предложение попадает в повестку и становится вопросом; дальше
живёт уже решение, а не предложение. Судьба решения — колонка «что с этим стало» в блоке
«Решения совета», и собирается она из истории правок. Смешивать их нельзя: иначе автор
предложения будет считать сделанным то, что совет ещё не принял.
