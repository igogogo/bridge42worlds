# ТЗ: корпусный граф — чтобы ИИ мог искать точки открытия

Заведено 2026-07-29, ML-инженер. Адресат — ведущая сессия (граф её зона, [ведущий.md](%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8/%D0%B2%D0%B5%D0%B4%D1%83%D1%89%D0%B8%D0%B9.md) задача 1).
Соседние документы: [ТЗ-ПОИСК.md](%D0%A2%D0%97-%D0%9F%D0%9E%D0%98%D0%A1%D0%9A.md), [задачи/ml.md](%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8/ml.md) задачи 4–5.

## Зачем

Нынешний `data/knowledge-graph.json` — справочник понятий: 773 узла (363 тега, 145 законов,
201 учёный, 64 раздела), 8044 ребра. Он отвечает на вопрос «что с чем связано» и хорошо
питает интерфейс.

Он **не может** ответить на вопрос, ради которого затевается направление: где искать новое.
Причина арифметическая, а не вкусовая. Главный сигнал поиска открытий формулируется так:

> два понятия близки по смыслу, но **ни разу не встретились в одной статье**

«Встретились в одной статье» считается по статьям. Статей в графе ноль. Дат нет. Значит
сигнал невычислим — не «плохо считается», а не считается вообще.

Появление векторов по статьям (DevOps задача 1) закрывает вторую половину — «близки по
смыслу». Осталось внести в граф первую: саму литературу.

---

## Что делаем

**Два файла, не один.** Это ключевое решение, и оно про производительность.

| Файл | Что | Кто читает |
|---|---|---|
| `data/knowledge-graph.json` | как сейчас, **не меняется** | браузер: `/graph/`, мини-графы |
| `data/corpus-graph.json` | новый, тяжёлый: статьи + даты + веса | только аналитика, в браузер не едет |

Почему раздельно: 1980 узлов статей (а в перспективе 100 000) обрушат страницу графа —
она рисует силовую раскладку в реальном времени. Смешивать витрину и аналитику нельзя.
`corpus-graph.json` не публикуется в R2, лежит рядом с `knowledge-graph.json`.

---

## Схема `corpus-graph.json`

```json
{
  "built": "2026-07-29",
  "articles": [
    {
      "id": "2410.01625",
      "date": "2024-10-02",
      "cat": "astro-ph.EP",
      "express": false,
      "tags": ["exoplanet", "planetary_density"],
      "laws": ["keplers_third_law"],
      "sci": ["Johannes Kepler"],
      "authors": ["Tucker Manton", "..."],
      "cited": ["2401.01234"],
      "vec": "2410.01625"
    }
  ],
  "concepts": [
    { "id": "t:exoplanet", "kind": "tag", "n": 214,
      "first": "2024-03-01", "last": "2026-07-20" }
  ],
  "cooc": [
    { "a": "t:exoplanet", "b": "t:planetary_density",
      "w": 37, "first": "2024-05-11", "last": "2026-07-18",
      "by_year": { "2024": 4, "2025": 11, "2026": 22 } }
  ]
}
```

Пояснения к полям, которых сейчас нигде нет:

- **`w`** — сколько статей содержат оба понятия. Сейчас рёбра бинарные, ранжировать нечем.
- **`first`/`last`/`by_year`** — когда связка появилась и куда движется. Без времени
  не работает ни один из сигналов ниже и невозможен ретроспективный тест.
- **`vec`** — ключ статьи в Vectorize. Это стык с DevOps: граф и вектор соединяются
  по нему, иначе два независимых мира.
- **`express`** — 1484 из 1980 статей сделаны по аннотации, а не по полному тексту.
  Их разметка беднее, и в сигналах их вес должен быть ниже. Флаг нужен, чтобы это
  вообще можно было учесть.

## Векторы понятий — без единого нового вызова модели

Вектор понятия = среднее векторов статей, в которых это понятие есть.

Ничего эмбеддить дополнительно не надо: эмбеддинги статей DevOps строит и так. Понятие
с `n < 5` вектора не получает — среднее по трём статьям это шум, а не смысл.

---

## Что граф обязан уметь выдавать

Граф не самоцель. Он принимается по трём запросам, которые на нём должны считаться.
Если запрос не считается — граф не готов, сколько бы узлов в нём ни было.

### С1. Непройденный мост

Пары понятий с высокой близостью векторов и **нулевой** со-встречаемостью.

Отбор: `cos(a,b) > порог` **и** `w(a,b) = 0` **и** оба понятия достаточно представлены
(`n ≥ 20` каждое — иначе это не «не встретились», а «мы про них почти ничего не знаем»).
Ранжирование по близости.

Это механизм Свонсона в чистом виде: две области говорят об одном и не читают друг друга.

### С2. Растущий стык

Связки, у которых `w` мала, но `by_year` растёт. Область сходится прямо сейчас —
хороший момент, чтобы посмотреть, что там ещё не сделано.

### С3. Мост между авторами

Автор X пишет про понятие A, автор Y про близкое B, общих статей нет. Кандидат на то,
что двое решают одну задачу разными словами.

Требует реальных авторов arXiv (856+), которых в едином графе сейчас нет — они лежат
отдельно в `authors-graph.json`. В корпусный граф их надо внести.

## Как строится

Новый скрипт `corpus_graph.py`, по образцу существующего `build_knowledge_graph.py`.

1. Прочитать все `lang/ru/archive/*/*/data.json`
2. Собрать узлы статей из готовых полей — `tags`, `laws`, `scientists`, `authors`,
   `date`, `categories`, `cited_arxiv`
3. Посчитать со-встречаемость всех пар понятий с разбивкой по годам
4. Записать `data/corpus-graph.json`

**Ни одного вызова LLM. Ни одного платного запроса.** Все данные уже лежат на диске,
это чистая пересборка. Стоимость прогона — минуты процессорного времени.

Запуск: отдельной командой `run.py corpus-graph`, не привязанной к пересборке сайта.

---

## Чего в этом ТЗ намеренно нет

- **Не трогаем `knowledge-graph.json`.** Витрина работает, ломать нечего.
- **Не строим векторные связи между понятиями** — это задача 1 ведущей сессии,
  отдельная и уже поставленная. Здесь только со-встречаемость и время.
- **Не публикуем в R2.** Файл аналитический, читателю не нужен.
- **Не выводим в интерфейс.** Сначала считаем сигналы и смотрим, есть ли они вообще.
  Показывать читателю ленту гипотез, не проверив их, — ровно та болталка, от которой
  мы отгораживаемся правилом про ссылки.

---

## Честное ограничение, которое надо знать заранее

**363 тега — это крупная сетка.** Настоящие системы поиска связей в литературе работают
на словарях в десятки тысяч понятий. На нашей сетке «непройденных мостов» может оказаться
мало просто потому, что тег слишком широкий: `black_hole` и `accretion_disk` встретятся
в первой же сотне статей, и никакого зазора между ними не останется.

Поэтому первое, что делаю после сборки, — **считаю, сколько пар-кандидатов вообще
существует**. Если их десяток, направление упирается не в граф, а в дробность разметки,
и это надо узнать до того, как построено что-то большое. Замер дешёвый, ответ важный.

## Рекомендации в спринт

Добавлено 2026-07-30 после замера. Обе рекомендации про одно: **сейчас граф не отличает
«работа этим пользуется» от «читателю это релевантно»**, и для поиска открытий это
решающая разница.

### Р1. Законы тянуть свободным списком, разносить по реестру после

Решение владельца 2026-07-30.

**Как сейчас.** Список законов подаётся модели в промпт, она выбирает из него. Отсюда
прямых связей **0,3 закона на статью** — короткий список работает потолком: чего в нём нет,
того статья «не использует».

**Как надо.** Модель называет законы **свободно, своими словами**, из текста работы.
Отдельным шагом названия разносятся по реестру: совпало — прямое ребро на известный закон,
не совпало — в список кандидатов на пополнение реестра.

**Почему с законами это проще, чем с тегами.** У законов имена каноничные и почти уникальные
(«третий закон Кеплера», «уравнения Максвелла»), их можно сопоставить с реестром надёжно.
Теги — придуманный нами управляемый словарь, свободное извлечение даст разнобой, который
нечем сводить. Поэтому приём применяем к законам, а к тегам — нет.

**Что это даёт помимо точности:**
- промпт короче — список из реестра в него больше не входит, это экономия на каждой статье
  (смыкается с пунктом 1 оптимизации стоимости у ведущей сессии);
- нет потолка: новые законы находятся сами и питают `run.py laws`;
- появляются **настоящие прямые рёбра** — то самое, чего не хватает сигналу С1.

**Грабли, которые надо обойти:**
- **Нормализация.** «уравнения Максвелла» / «Maxwell's equations» / `maxwells_equations` —
  одно и то же. Сводить по эмбеддингу названия, не по строке.
- **В реестре уже есть битый идентификатор** — `schrdinger_equation` (потеряна «ö» при
  транслитерации). Сопоставление по строке на нём сломается; заодно стоит починить сам id.
- **Выдумки.** Модель назовёт закон, которого в работе нет. Требовать цитату — фрагмент
  текста, где закон упомянут; нет фрагмента — связь не засчитываем.
- **Кандидаты не добавлять в реестр автоматически.** Список на просмотр человеком,
  иначе реестр зарастёт синонимами и опечатками.

### Р2. У каждого ребра — происхождение

Замер 2026-07-29: через теги получается **25,7 закона на статью** и 96% покрытие, но это
артефакт транзитивности. `holographic_principle` оказывается в 1066 статьях из 2016 —
он просто подвешен к частому тегу. Со-встречаемость законов из-за этого пересыщена:
при n≥20 не встретились всего 1,3% пар против 31% у тегов. Зазоров не осталось —
и сигнала тоже.

Поэтому в `corpus-graph.json` у ребра обязательно поле `src`:

| `src` | Откуда | Годится для |
|---|---|---|
| `direct` | сущность названа в самой статье | сигналы С1–С3, обучающие данные |
| `derived` | получена через справочник (статья → тег → закон) | поиск, навигация, «похожее» |

**Смешивать нельзя.** На производных рёбрах граф сам изготавливает со-встречаемость,
которой в науке не было, и кандидаты на открытие исчезают до всякого фильтра.

То же касается учёных: 3739 рёбер учёный–тег — производные. «Гейзенберг связан со статьёй»
означает ровно «в статье есть тег, к которому подвешен Гейзенберг».

## Готово, когда

- `data/corpus-graph.json` собирается одной командой из `data.json`, без обращений к API
- в нём 1980 узлов статей с датами, со-встречаемость понятий с весами и разбивкой по годам,
  реальные авторы arXiv
- считаются все три сигнала С1–С3, и по каждому есть **число кандидатов** — не «работает»,
  а сколько именно нашлось
- ретроспективная проверка возможна: срез по дате отсекает поздние статьи, и сигналы
  пересчитываются на усечённом корпусе
